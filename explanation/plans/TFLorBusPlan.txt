# Rerouting System — Implementation Plan

---

## Context
The current prototype only selects a best route once at journey start. This plan introduces a two-group agent architecture: an **Analyzer Agent** that selects the best route from TfL data based on user constraints, and a **Guide Agent** that monitors the journey every 20 seconds and triggers a reroute popup if a significantly better option appears.

---

## Architecture Overview

```
User taps Bus or TfL button
        │
        ▼
┌─────────────────┐
│  Analyzer Agent │  ← runs on backend (Node.js)
│  (bus OR tfl)   │  ← calls scoreRoute.js ranking
└────────┬────────┘
         │ bestRoute + allRoutes
         ▼
  RouteScreen / RoutesScreen
         │ "Start journey"
         ▼
┌──────────────────┐
│   Guide Agent    │  ← runs in frontend (OnRouteScreen)
│  (polling loop)  │  ← GPS watchPosition + 20s interval
└────────┬─────────┘
         │ delay on next step detected
         ▼
  Reroute Popup (15s auto-accept)
```

---

## Part 1 — Analyzer Agent

### Mode Groups
| Button label | `transportGroup` | Modes included |
|---|---|---|
| Bus | `bus` | `bus` only |
| TfL | `tfl` | `bus` + `tube` + `train` |
| Car / Walk | unchanged | existing single-mode filter |

### Backend changes

**`server.js`** — new endpoint `POST /api/analyze-route`
- Accepts `{ destinationId, transportGroup, userProfile, currentRouteId, currentLegId }`
- `transportGroup: 'bus'` → `modeFilter: 'bus'`
- `transportGroup: 'tfl'` → no single modeFilter — filter routes where `mode ∈ ['bus','tube','train']` after loading
- Calls existing `buildRecommendationInput()` + `recommendRoute()` — no new scoring logic
- Returns `{ bestRoute, allRoutes, explanation, shouldReroute, rerouteTrigger }`

**`dataIntegration.js`** — extend `buildRecommendationInput` to accept `modeSet: string[]`
- If `modeSet` provided: `routes.filter(r => modeSet.includes(r.mode))`
- If `modeFilter` (single string) provided: existing behaviour unchanged
- If neither: all routes

### Accessibility scoring (within existing `scoreRoute.js`)
The existing penalty weights already handle this correctly:
- Accessibility users: step-free penalty (+100), lift-out-of-service (+120), walking×1.5, transfers×4
- Regular users: ETA weight dominates

No changes needed to `scoreRoute.js`.

### Frontend mode changes

**`frontend/data.jsx`** — add `analyzeBusRoute` and `analyzeTflRoute` helpers that call `POST /api/analyze-route`

**`frontend/screens.jsx` (ConvoScreen)** — replace the 4-mode tile grid with:
- Bus tile (`transportGroup: 'bus'`)
- TfL tile (`transportGroup: 'tfl'`, bus + underground)
- Car tile (unchanged)
- Walk tile (unchanged)

---

## Part 2 — Guide Agent (frontend polling loop)

### GPS tracking upgrade
- Replace one-shot `getUserLocation()` in `app.jsx` with `navigator.geolocation.watchPosition()` so `originCoord` updates in real-time during the onroute screen

### Current-step detection
In OnRouteScreen, track which leg the user is on:
- Compare live GPS to each leg's `to` coord using Haversine distance
- "Current leg" = the first leg whose `to` coord is more than 50m ahead
- "Next step" = leg immediately after current leg

### 20-second polling loop
```
setInterval (20s) — only while screen === 'onroute' AND GPS is moving (speed > 0 or position changed)
  → POST /api/analyze-route with:
      { destinationId, transportGroup, userProfile,
        currentRouteId: activeRoute.id,
        currentLegId: detectedCurrentLeg.leg_id }
  → if shouldReroute === true AND newRoute.id !== activeRoute.id:
      → show RerouteModal
```

### RerouteModal
- Uses existing `.modal-backdrop` + `.modal` CSS (already in styles.css)
- 15-second countdown displayed
- "Stay on route" button → dismiss, cancel timer
- If timer reaches 0 → auto-accept: update `activeRoute`, continue guiding
- Structure similar to existing `ModeMenu` component in screens.jsx (lines 295-312)

### Route caching
- Guide Agent holds only `activeRoute` (the chosen route object) in state
- `alternativeRoutes` from the Analyzer are stored in a ref (not state) — available for reroute comparison without causing re-renders
- On reroute: swap `activeRoute` to `newRoute`, update ref

## Follow-up questions for you

**Q1 — Agent implementation style**: Should the Analyzer Agent be:
- **(A) A deterministic function** — extend existing `scoreRoute.js` / `dataIntegration.js` logic (fast, no extra dependencies)
- **(B) An LLM-backed agent** — use Claude API or Ollama to reason about route trade-offs in natural language (slower, adds the AI layer that the hackathon is built around)

**Q2 — TfL button placement**: Should the existing "Tube/Underground" button be *replaced* by the TfL tile, or should TfL be a *5th option* added alongside the current 4?

**Q3 — Reroute check scope**: When the Guide Agent polls every 20 seconds, should it:
- **(A) Only alert if the NEXT step specifically has a delay/disruption** (as described)
- **(B) Also alert if there's a completely better route that avoids the current one entirely** (e.g., take bus instead of tube)

**Q4 — Real TfL API vs static data**: For the prototype, should the Analyzer call the real TfL Journey Planner API for live disruption data, or continue using the static `route_data_*.json` + `traffic_events.json` files (with manually set `active: true` events for demo purposes)?

**Q5 — GPS "is moving" detection**: Should the 20-second polling fire:
- **(A) Always** while on the onroute screen (even if stationary)
- **(B) Only when GPS position has changed** since the last poll

**Files to change**:
